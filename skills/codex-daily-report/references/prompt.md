# WorkItem Synthesis Router

日报模型输入为当天 EvidenceBundle，唯一允许的模型产物为 WorkItemBundle。完整字段、范围优先级、事实同源、归并和状态规则见 `work-item-contract.md`。不得直接生成或修改最终 Markdown。

## 领导版事项表达

`submitted_text` 和 `weekly_text` 是已经开展工作的汇报口径，不是排查过程记录或个人待办。必须区分“本次工作交付已完成”和“发现的风险尚未彻底解决”：完成巡检窗口、形成报告并得到风险结论，即表示巡检工作已形成阶段性成果；不能仅因风险仍需治理或业务映射资料不完整，就把整项巡检写成 `in_progress` 或“持续排查”。

生成领导版前，对每个分句做语义归类，而不是只检查几个关键词：①已完成动作；②已形成事实或结论；③未来动作；④内部过程状态。正文只保留①②；③进入 `follow_up` 或独立计划，④删除或改写为结论边界。移除③④后若没有具体完成动作、阶段交付或可核查结论，该事项保留在 WorkItem JSON，但不得进入本周重点工作；不得为了保留条目虚构完成态。

“已完成动作”不要求整个项目终结。等保、审计、跨部门取数、工单协作等配合类工作，只要证据表明当周确实开展了具体配合，就可以报告该已发生的工作切片；使用“已配合……开展数据信息获取与对接，明确本次协作内容……”等口径，不追加“持续推进”。整体事项仍可在 JSON 中保持 `in_progress`。

- 先写已完成的范围和动作，再写已识别事实、结论或交付物，最后以已形成的结果或结论边界收尾。
- JSON 的 `status` 是内部结构化字段，不在领导版正文中直译为“状态为持续排查”“状态为进行中”等流程标签。
- `follow_up` 与“下一步……”只保留在结构化字段或独立计划段，不得拼接到本周事项、日报事项或 `weekly_text` 末尾。
- 不得把尚未执行的动作包装成条件式或伪完成结果，例如“完成授权后可重试”“补齐权限后即可验证”“当前为方案分析完成，待账号执行”“已明确优先处理慢 SQL”。若本次只完成分析或方案，应以“定位卡点并形成处理方案”“完成方案核验并明确风险”“确认主要风险集中于……”收尾；只有证据证明已实际执行时，才能写“已补齐权限并完成验证”。
- 资料不足但不影响本次交付成立时，改写成结论边界，例如“受现有实例与业务链路映射覆盖限制，本次结论按实例维度汇总，不延伸判断业务链路归属”，不得写成“当前缺少证据，持续排查，下一步对齐……”。
- 只有报告、巡检窗口或分析本身尚未完成时才使用 `in_progress`。如果只是后续整改、归属确认或风险治理尚未完成，本次已完成的巡检/分析仍按证据使用 `analysis_complete`，后续动作放入 `follow_up`。
- 确需领导关注阻塞时，仍先写已经完成的阶段成果，再客观说明外部依赖及其影响；不得只汇报未完成状态或用待办收尾。
- “持续推进、继续排查、持续跟进”只表示过程，没有阶段成果时不构成领导版事项；有阶段成果时只报告已经完成的部分，不追加过程尾句。
- 用户明确指定领导版分类时优先遵从。等保合规资料配合以跨部门、审计或制度协作为主时，归入“五、其他重点事项”，不能因为底层对象涉及数据或权限而机械归入数据治理。

示例：

- 不合格：`针对 analyse-bigdata(readonly-mall) 进行多窗口巡检，当前缺少业务链路映射证据，状态为持续排查，下一步对齐连接实例、慢日志与事务/锁等待。`
- 合格：`已完成 analyse-bigdata(readonly-mall) 多窗口巡检，识别 select_scan、tmp_disk_tables 高风险告警；本次采样未发现平均耗时超过 1000ms 的慢 SQL 模板，巡检结论已按实例维度汇总。`
- 不合格：`定位到 REPLICATION CLIENT/SLAVE 缺失为卡点，完成授予后可重试位点初始化。`
- 合格：`已完成 CloudCanal 同步任务账号权限核查，定位 REPLICATION CLIENT/SLAVE 权限缺失为位点初始化卡点，并形成权限补齐与连接重建处理方案。`
- 不合格：`当前为方案分析完成，待授权账号执行并验证。`
- 合格：`已完成目标表补充日志方案核验，确认语法、检查口径及执行风险，形成配置与验证方案。`
- 不合格：`已明确优先处理慢 SQL、批处理并发与高回滚。`
- 合格：`确认主要风险集中于慢 SQL、批处理并发和高回滚。`

## follow_up 与下周计划口径

证据存在明确后续动作时，`follow_up` 用于记录该事项下一步要做什么，包括当天或短时间内即可闭环的动作；它不是“下周重点工作”的同义字段。`follow_up` 应写成简洁、可执行、可验证的动作，而不是当前状态、依赖说明或原始技术命令：

- 固定结构为“行动目标 + 对象或范围 + 验收结果”，通常控制在 35–100 个中文字符。
- 以“完成、推进、开展、复核、验证、优化、落实、协调、整理、输出、补齐、持续开展”等行动词开头。
- 一项只表达一个管理目标；同一目标下的技术动作可以合并，不把多个无关对象、命令和检查项挤在一项里。
- 把 `SHOW MASTER STATUS`、`DBA_LOG_GROUPS`、DDL 等命令翻译成“验证复制位点可用”“核对补充日志状态”“输出执行结果”等验收口径。对象标识对识别工作不可缺少时可以保留，但不得直接粘贴 SQL、命令、本地路径或端口。
- 存在前置依赖时写成主动推进动作，例如“推进账号权限补齐与连接重建”，不得以“补齐权限后”“等待对方完成后”开头。
- 周期巡检可以使用“持续开展”，但必须同时写明巡检范围、重点关注方向以及报告、清单或复核结论等交付结果。
- 证据只有建议而没有已确认的后续安排时，`follow_up` 保持空字符串；不得为了凑下周计划编造责任方、期限、指标或交付物。

周报生成前先对全部非空 `follow_up` 做“跨周必要性”筛选，再做文字审查。只有以下事项可进入“下周重点工作”：

- 按周或固定周期持续开展的巡检、报告、复核或运营任务。
- 需要多日观察、趋势验证或下一周期复核才能得出结论的风险事项。
- 分阶段推进的整改、治理、迁移、改造、专项或架构工作。
- 已明确安排在下周日期或变更窗口执行的工作。
- 因跨团队、跨部门或外部依赖，本周客观无法闭环且下周仍需推进的工作。

权限补齐、连接重建、位点初始化、补充日志配置、日志组状态核对、执行一次 SQL/DDL 后验证、单次重跑或复测等“执行后即可立即知道结果”的动作，不进入下周计划；当前尚未执行或当前回合结束也不能自动视为跨周工作。筛选后按管理优先级选择 0–3 个目标，合并重复目标，清除技术执行细节；没有真正跨周事项时省略整个“下周重点工作”段落，不得凑数。若历史 WorkItem 的 `follow_up` 不符合计划口径，使用带来源引用的 `weekly-revise` 保存周级计划修订，不为润色周报而改写已验证的每日事实。
